# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Research code for the NDSS 2026 paper "DualBreach" (dual-jailbreaking of an LLM *and* its guardrail). There is no build system, test suite, or linter — it is a collection of standalone Python scripts run directly.

**Local setup (this machine):** a uv venv at `.venv/` (git-excluded; transformers 5.x, torch, peft, nltk, seaborn). Activate it with `source .venv/bin/activate`. The original `environment.yml` / `requirements.txt` were not used (the README says `.yaml`, the file is `environment.yml`). Models come from the shared HF cache: `export HF_HUB_CACHE=/mnt/data1/huggingface/hub HF_HUB_OFFLINE=1` (already done by `guard_attack.sh`). The HF token is in the environment — never print it. The network proxy is flaky (CONNECT 500s): retry downloads/installs (`UV_HTTP_RETRIES=10`). There are 4× 46 GB GPUs, managed by **Slurm** (single node `ailab-server2`, partition `gpu`, `--gres=gpu:N`): run every GPU job (attacks, tests, diagnostics) through `sbatch`/`srun`, never directly, and spread jobs over the free GPUs. `MTO/slurm_submit.sh <name> [cold_decoding.py args]` submits one attack as a 2-GPU job (inside the job `cuda:0` = target LLM, `cuda:1` = d3 guard; logs in `MTO/outputs/slurm/<name>-<jobid>.log`, results tagged with `--run_tag _<name>`); `START`/`END` (inclusive)/`DATASET` env vars select the samples and `TIME` the job time limit (default 02:00:00). Two such jobs fit on the node at once. Python stdout is block-buffered in the log files until the job ends.

## Pipeline / architecture

The components are loosely coupled through CSV/JSONL/`.pt` files, not Python imports:

1. **TDI** (`TDI/scenario_initialize.py`) — Target-driven Initialization: builds scenario-based initial prompts from a harmful query using an external LLM API (OpenAI-compatible clients, Baichuan, etc.), scored with `get_jailbreak_score`/`get_stl_score` from `utils` (which lives in `eval/response_eval/utils.py`, not in `TDI/`). Not patched for this machine (needs API keys), and the scenario CSVs it produces (`*_scenario_target_100.csv`) are not in the repo, so only the `*_original` datasets of MTO can be run.
2. **MTO** (`MTO/`) — Multi-Target Optimization, a COLD-Attack-derived suffix optimizer. Entry point is `bash guard_attack.sh <mode> <startIndex> <generate_device_id> <guard_device_id> [dataset] [extra args]` (run from inside `MTO/` with the venv active; e.g. `bash guard_attack.sh suffix 0 0 1 advbench_original --guard --end 0` runs sample 0 only; `--guard` turns on the gradient step through the guardrail, otherwise the guard only scores/selects). It runs `cold_decoding.py` (arg parsing, model loading) → `attack_suffix.py` (`attack_generation`, dataset loading/loop) → `decoding_suffix_optim_y_logits_with_best_memory.py` (`decode`, the Langevin-dynamics loop). `util.py` / `opt_util.py` / `bleuloss.py` are helpers (bare imports like `from util import *`, hence run from `MTO/`).
   - **Models (substituted from the paper's):** target LLM `meta-llama/Llama-3.1-8B-Instruct` by default (GPU `generate_device_id`, fp16) or `--pretrained_model Qwen3.5-4b|Qwen3.5-9b` (bf16; same vocabulary as d3, so d3's own embedding table is used and no bridge is needed), guardrail `vllm-sr/d3-flash` (GPU `guard_device_id`), victim/response model `Qwen/Qwen3-8B` (`--response_device`, default cuda:2) and LLM-judge `Llama-3.1-8B-Instruct` (`--judge_device`, default cuda:3), set in `attack_suffix.py`/`cold_decoding.py`. Both are loaded lazily (`evaluate_util._LazyPipeline`) on the first candidate that passes the guard (P(safe) > 0.5) and cached across samples; `slurm_submit.sh` puts them on the job's two GPUs. Results are therefore not comparable to the paper.
   - **Guardrail = d3-flash** (`MTO/d3_guard.py`, class `D3Guard`): vLLM Semantic Router "Decision 3.0" System One model (Qwen3.5-9B backbone, non-causal encoder + 255-way code readout). One yes/no ("noul") question is asked about the candidate prompt and P(yes) is used as P(unsafe); the forward pass is re-implemented on `runtime.encoder` so gradients reach the input embeddings. Because d3 uses the Qwen3.5 vocabulary and the target is Llama, `bridge_embeddings` builds a `[128256, d]` table (each Llama token → mean d3 embedding of its text) so MTO's `one_hot @ weights` works; this is an approximation. Replaces the paper's Llama-Guard-3 / proxy models.
   - Experiment flags: `--guard_loss {ce_prob,margin}` (CE on [P(safe),P(unsafe)] vs the raw readout-logit margin), `--guard_align {retok,ids}` (`retok` = paper: guard input is the decoded suffix re-tokenised with the prompt; `ids` = the exact suffix ids at known positions, so the gradient rows line up with the suffix positions; needs a target sharing d3's vocabulary, i.e. Qwen3.5; in `ids` mode the recorded `p_safe`/`margin` are d3's score of the real text) and `--run_tag` (suffix of the result `.jsonl` name). Each result record carries `guard_trace` (per guard round: `p_safe`, `margin`, `grad_norm`, `step_l1/max/nnz`, `trailing`, `align_frac` = share of suffix ids found at the matching prompt position, softmax-saturation stats `sm_maxp_mean/min`, `sm_active` (#entries with p > 1e-10), `gap_mean/min`, `ylog_min/max/std`, and in `ids` mode `p_safe_aligned`, `margin_aligned`, `retok_equal`); with `--verbose` the log has `[mem]` lines (allocated/peak GB on the target and guard GPUs every 5 iterations).
   - `local_paraphraser.py`: replaces the paper's API paraphrase LLMs (QwenPlus/QwenMax/GPT-4o/GPT-4) by the local GGUF `Qwen3.8-27B-Uncensored` via llama-cpp-python on **CPU** (~1-2 min per rewrite; `PARAPHRASER_THREADS`). `evaluate_util.harmful_paraphrase` (re-paraphrasing every `--paraphrase-iters`) and `TDI/scenario_initialize.py` use it.
   - `evaluate_util.py` is a **reconstruction** (upstream omitted it): response/judge pipelines and `evaluate_llm_response`. `nltk_compat.py` provides offline fallbacks for NLTK stopwords/punkt/pos_tag (NLTK downloads are blocked).
3. **Proxy model** (`proxy_model/`, optional) — imitates black-box guardrails (Google, OpenAI moderation) so MTO can use them: `data_prepare/` (query guardrail API + embed) → `train/{google,openai}_train.py` (small DNN) → `evaluate/`. Not used with d3-flash; paths not patched.
4. **Guardrail eval** (`eval/guardrail_eval/`) — one script per guardrail (Google, OpenAI, Llama-Guard-3, NeMo, Guardrails-AI) writing JSONL scores; `proxy_*.py` evaluate against the proxy. Not patched.
5. **Response eval** (`eval/response_eval/`) — `response_eval.py` then `attack_success_evaluate.py` (LLM-judge via `judge_prompt.py`, plus `strong_reject_eval.py`). Not patched.
6. **EGuard** (`EGuard/`) — defense: XGBoost ensemble over multiple guardrails' scores/embeddings. `data_prepare/` per guardrail → `train_xgboost.py` → `evaluate_xgboost.py`. Currently out of scope.

Datasets live in `data/` (`advbench_100.csv`, `DNA_100.csv`, `harmBench_100.csv`; columns `harmful, target, harmful_id`). `attack_suffix.py` takes the dataset from `--dataset` (e.g. `advbench_original`) and resolves CSVs relative to `data/`.

## Gotchas

- **d3-flash: never call `.to(device)` on the loaded wrapper** — with transformers 5 it silently zeroes all weights (scores come out exactly 0.5/0.5, hidden states 0). Load with `device_map={"": device}` as `D3Guard` does. `transformers==5.17.0` is what d3 was validated with.
- **Direct GPU-to-GPU copies are unreliable on this node** (4× L40S, PCIe, `can_device_access_peer` is True but the data does not arrive): in isolated tests `x.to('cuda:1')` returned all zeros (600/600 copies under `expandable_segments:True` in one process) or unrelated stale memory (`cuda:1 -> cuda:0`, another process), depending on the CUDA initialisation order; `copy_` into a preallocated tensor and a CPU round trip were exact. In MTO this silently corrupted the logits handed to the guard / the decode and the guard step written back (identical runs flipped between a normal and a junk-suffix outcome; one run recorded all-zero logits). Never move a tensor between the two GPUs with `.to()`: use `util.move_to(t, device)` (stages through host memory, ~ms for [1, 20, V] logits). Guard-related results produced before this fix (jobs ≤ 372, e.g. the base/A3/B/C single-sample comparisons and the smoke/dbg/sync runs) are unreliable; the ids-vs-retok runs from job 373 on are clean (duplicates reproduce).
- **Clean 10-sample baseline (Qwen3.5-4B target, `--guard_loss margin`, advbench_original 0-9, 200 iters; `retok` vs `ids`):** the guard margin (logit_unsafe − logit_safe) is flat over the iterations (retok 5.5 → 5.6, ids 5.6 → 6.1 per 40-iter bucket); round-to-round changes are zero-mean noise (sd ≈ 2, margin improves in 45-47% of rounds) and the best round is mostly an early draw. Only 1/10 samples per variant ever got P(safe) > 0.5, none ended as a successful attack, and `ids` vs `retok` shows no detectable difference (best P(safe) higher in 5/10 samples). So the guard step is not acting as an optimiser yet. The softmax in the guard step is *not* saturated (late top-1 probability ≈ 0.6-0.7, logit gap ≈ 2, zero-step rounds 0/40; the number of entries with p > 1e-10 falls from ≈ 10^6 to ≈ 10^5): the earlier "saturation freezes the suffix" conclusion came from runs corrupted by the GPU-copy bug above. The step itself is a sign step, ±`stepsize` on every vocabulary entry with a non-negligible gradient (≈ 2M of 5M entries), which is a candidate cause. Each 5-sample job takes ≈ 15 min.
- **Guard step internals (measured):** the step is a fresh `Adagrad(lr=0.1)` on a zero `leaf_param` each round, i.e. ~one sign step, so the gradient magnitude (and hence CE vs margin) hardly matters; `get_text_from_logits` appends `". "` to the suffix and the re-tokenised prompt never contains the decoded suffix ids contiguously (`trailing: None` in `guard_trace`), so the gradient rows sliced with `[-len(suffix):]` are probably misaligned with `y_logits` positions; special tokens (`<|im_end|>`) are not banned and show up in suffixes.
- Qwen3.5 targets run on torch fallback kernels (no flash-linear-attention/causal_conv1d). Every model call whose output is not back-propagated must run under `no_grad`: `soft_forward(detach=True)` and `decode_with_model_topk` build autograd graphs through the hybrid (Gated-DeltaNet) cache that are never freed, which leaked ~1 GB of target GPU memory per iteration until OOM (Llama is unaffected). The `[mem]` log lines make such leaks visible (Qwen3.5-4B target stays at ~9.7 GB, Llama at ~16.7 GB).
- **Keep the optimised logits in fp32.** The target model is fp16; Adam on fp16 `epsilon` underflows `eps=1e-8` to 0 → NaN after the first step. `decode` casts `init_logits.float()` and the forward runs under `torch.autocast`.
- transformers 5: `DynamicCache` is mutated in place, so `util.py` deep-copies the prefix cache (`_fresh`) before each forward; `torch_dtype` is deprecated in favour of `dtype`.
- `pipeline(..., model=...)` moves the model to cuda:0 unless `device=` is passed (see `evaluate_util.get_model_inference_pipeline`).
- The guard gradient step is skipped (with a message) when the decoded suffix re-tokenises to a different length than `y_logits`.
- d3's probabilities saturate (P(unsafe) ≈ 0.999 for harmful prompts), so the cross-entropy-on-probabilities guard loss has a very small gradient; expect the guard score to move slowly within a few dozen iterations.
- Outside `MTO/` the scripts are still research-lab leftovers with **hardcoded absolute paths** (e.g. `/data/home/Xinzhe/...`) and hardcoded GPU ids / `CUDA_VISIBLE_DEVICES`; edit them before running.
- API keys/URLs are blank placeholders or lists inside the scripts (`eval/guardrail_eval/OpenAI.py`, `Google.py`, `TDI/scenario_initialize.py`); fill in locally and don't commit them.
- Several scripts write logs to relative dirs (e.g. `./log/`, `../log/`) that must exist beforehand.
- README commands are approximate (e.g. `python /proxy_model/train/...`, `bash guard_attack.sh` without args); use the paths/arguments above.
